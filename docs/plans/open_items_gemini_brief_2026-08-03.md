# Бриф для Gemini Pro: невирішені пункти Vydra (kindle-butch-gen)

## Як користуватись цим брифом

Це не готове дослідницьке завдання одного проходу — це список усього, що
лишилось невирішеним після двох Opus-планів цього проєкту
(`TASK-90_plan.md` — докsbook-конвеєр + локальна редакторська модель, і
`book_publication_quality_implementation_plan.md` — публікаційна якість
книг). Власник проходить пункти **послідовно, в чаті з Gemini Pro**,
разом зі свіжим повним дампом коду репозиторію (PDF, додається окремо
власником). Для кожного пункту нижче:

1. Знайди й прочитай точний файл:рядок у прикладеному PDF.
2. Підтверди, що поточна поведінка в коді збігається з описом нижче
   (код міг змінитися — якщо розбіжність, скажи прямо, не припускай).
3. Допоможи власнику сформулювати конкретне рішення — не просто
   "варіанти", а по факту прийняте рішення з обґрунтуванням, готове
   для передачі назад Claude Code на реалізацію.
4. Переходь до наступного пункту лише після того, як власник явно
   підтвердив рішення по поточному.

Пункти впорядковані приблизно за пріоритетом (Частина A — найдешевші й
найважливіші технічні баги; Частина B — рішення власника з реальним
судженням; Частина C — окремий план публікаційної якості).

**Формат матеріалу, який власник принесе назад Claude Code**: по
кожному вирішеному пункту — сама ухвала (що робимо) + коротке
обґрунтування (чому саме так). Без потреби писати код самому — це
робить Claude Code після.

## Частина A — Рівень 1: реальні баги на вже робочому функціоналі (TASK-90)

Технічні, невеликий простір для дискусії — здебільшого потрібно
підтвердити підхід до фіксу, не довге обговорення.

### A.1 — Stage 5 степпер губить стадії `merge`/`error`
Файл: `frontend/src/pages/BookPipelineView.tsx`.
`KNOWN_STAGES` (~рядки 47-55) не містить стадій `merge` (пишеться
`bin/run_book_pipeline.py:299`) і `error` (`:418,422`). Через
`findIndex` → `-1` (~рядки 70-72) під час стадії `merge` весь степер
візуально скидається в нуль — виглядає так, ніби прогін почався
заново. Не крашить (є fallback), але вводить в оману.
**Питання Gemini**: підтвердити фікс — додати `{ key: 'merge', label:
'Merge' }` між `editor_review` і `book_compile_en`, окремо стилізувати
`error` (rose-колір) — чи є краще рішення?

### A.2 — `stop_conversion_api` graceful-shutdown мертвий код + відсутній killpg
Файл: `kbg_web/app.py`, функція `stop_conversion_api` (~рядки
1051-1084). `return jsonify(...)` спрацьовує РАНІШЕ за
`terminate()`/`wait(timeout=3)`/`kill()`-ескалацію нижче — вони ніколи
не виконуються, Stop завжди йде через голий SIGKILL
(`os.kill(pid, SIGKILL)`/`proc.kill()`), ніколи `os.killpg`. Пов'язано
з Q-14/Q-16 нижче (Частина B) — осиротілі дочірні процеси всередині
proot переживають SIGKILL батька.
**Питання Gemini**: підтвердити порядок дій — спершу додати
`start_new_session=True` у місця спавну процесів (`app.py:969,1034`,
`run_conversion_batches.py:32,72`, `cast_ner_prepass.py:223`), **потім**
портувати `killpg`-з-fallback блок із `book_pipeline_stop` в
`stop_conversion_api` (порядок критичний — killpg на процесі, який
стартував БЕЗ `start_new_session=True`, засигналить групу самого
Flask).

### A.3 — `flags_pending` рахує невирішені прапорці як вирішені
Файл: `kbg_web/book_pipeline.py` (~рядки 163-164). Лічильник вважає
прапорець вирішеним, щойно з'являється БУДЬ-ЯКИЙ edit-рядок для його
`flag_id`, незалежно від статусу — клік "Apply" одразу обнуляє badge
"pending", хоча ще нічого не затверджено.
**Питання Gemini**: підтвердити фікс — фільтрувати `list_edits` до
`status in ("approved", "discarded")`.

### A.4 — Витік файлових дескрипторів на кожному старті/стопі пайплайна
Файли: `kbg_web/app.py:965,1033`, `kbg_web/book_pipeline.py:112`.
`log_file = open(log_path, "a")` передається в `Popen` і ніколи не
закривається в батьківському процесі — по одному fd на кожен
старт/стоп у довгоживучому Flask-процесі.
**Питання Gemini**: підтвердити фікс — закривати handle одразу після
повернення `Popen` (дитина тримає власний dup, батьківському handle
далі не потрібен).

## Частина B — Q-питання власника (TASK-90), потребують реального судження

### Q-2 — Незакомічена робота
Стан на момент останнього запису плану: ~40 незакомічених файлів,
один реальний ризик деплою (розгіноровані бандли). **Перевір поточний
`git status` у прикладеному дампі — стан міг змінитися з того часу.**
**Питання**: комітити/stash/окрема гілка перед подальшою роботою?

### Q-3 — "Прапорець, ніколи авто-застосування"
Дизайн-рішення book_editor: прапорці fact_drift/translation_hostile —
завжди пропозиції для людини, ніколи не застосовуються автоматично.
**Питання**: це справді бажана поведінка назавжди, чи є сценарій, де
власник хоче повну авто-заміну переписування без рев'ю?

### Q-4 — Async-архітектура
Раніше прийнято рішення "черга не потрібна" (для book_editor
model-calls). **Питання**: ратифікувати остаточно, чи є підстави
переглянути з огляду на все зроблене відтоді (Stage 9 live-тест
сьогодні)?

### Q-6 — `ModesView.tsx` мертва заглушка
Frontend-компонент існує, не підключений. **Питання**: лишити просто
карткою, картка+навігація без функціоналу, чи повне підключення до
чогось реального?

### Q-8 — Технічна книга отримує TTS?
Docsbook-книги (гуманізована технічна документація) — чи повинні
отримувати аудіокнижну стадію так само, як звичайні книги, чи це
осмислено лише для художньої прози?

### Q-10 — Нумерація TASK
`TASK-90` — заглушка-номер, реального відповідного запису в `TASKS.md`
немає (доходить до TASK-67; `common/mqm_review.py` посилається на
TASK-88 — теж, схоже, не існуючий). **Питання**: призначити реальний
номер, і чи варто одразу навести лад у всіх таких "дірках" нумерації?

### Q-14 / Q-16 — Осиротілі proot-процеси переживають kill батька (реальний тепловий інцидент, підтверджено фізично)
Файли: `audio_stage.py`, `tts_helper.py`, `kbg_web/app.py` (кілька
місць спавну процесів), `kbg_web/book_pipeline.py` (`book_pipeline_stop`,
частково закрито `os.killpg`). Підтверджений живий інцидент: тестовий
прогін лишив `tts_helper.py` усередині proot Ubuntu молотити CPU на
500%+ навіть після kill батьківського PID — телефон реально нагрівся
(виявлено власником фізично). Root cause: proot не гарантує, що kill
батька вб'є все дерево процесів; потрібен явний `start_new_session=True`
+ `killpg`, а не покладання на kill одного PID. Частково вже зроблено
для деяких спавнерів (`book_pipeline.py:115`, кілька місць в `app.py`,
`bin/resume_active_conversion.py:128`), **відсутнє саме там, де стався
оригінальний інцидент**: `app.py:1034` (`run_audio_api`→`audio_stage.py`),
`app.py:969` (`run_conversion_api`→`run_conversion_batches.py`),
`common/utils.py:110`, `bin/cast_ner_prepass.py:223`.
**Питання**: підтвердити повний список місць, що потребують
`start_new_session=True`, і чи є ще неврахований спавнер поза цим
списком (перевірити прикладеним дампом коду).

### Q-17 — Вкладені заголовки з шляхом-у-дужках систематично губляться при перекладі
Файл: `translate_stage.py` / `common/utils.py` (валідація перекладу).
Патерн `##### Terminal Character (zellij-server/src/panes/terminal_character.rs)`
— заголовок функції/файлу з посиланням на вихідний файл одразу після —
Hy-MT2 стабільно (3/3 спроби, різні температури) губить маркер `#` саме
для цього класу заголовків. Це типова конструкція технічної
документації (не рідкість) — тобто валідація, найімовірніше
калібрована на художню прозу, систематично блокуватиме docsbook-книги
частіше, ніж прозові переклади. Три досліджені обхідні шляхи НЕ
допомогли (прибрати дужки — ні; знизити рівень заголовка — ні; повністю
прибрати `#`-маркер — теж ні, і сам експеримент виявився ненадійним,
підозра на неправильні межі сегмента).
**Питання, три варіанти з плану, жоден не обраний**:
(а) послабити валідацію конкретно для docsbook-пайплайну,
(б) додати pre-translation крок, що тимчасово ховає шлях-у-дужках і
    повертає після перекладу (аналог наявного `PlaceholderManager`),
(в) прийняти як відомий ручний edge case для людського рев'ю.
Пов'язано з Q-19's залишком (Частина, вже закрита раніше цієї сесії) —
той самий структурований `segments_degraded`-сигнал міг би позначати й
цей клас окремо, якщо буде корисно для рішення.
