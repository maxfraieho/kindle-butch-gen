# Промт для Gemini Deep Research: пошук преміальної OCR-моделі для манги (Vydra)

> Скопіюй усе нижче в Gemini Deep Research (Gemini Pro) одним повідомленням.

---

Ти — дослідник на перетині on-device ML inference (мобільні GPU/NPU, GGUF/llama.cpp, ONNX Runtime) і computer vision для manga/comic OCR. Проведи глибоке OSINT-дослідження і запропонуй **конкретну, реалістичну модель(і)** для преміального (платного) рівня розпізнавання тексту в манзі в описаному нижче продукті. Не обмежуйся GGUF/llama.cpp — активно шукай і ONNX, і інші runtime-варіанти. Шукай англомовні першоджерела (model cards на HuggingFace, GitHub issues/PR llama.cpp й ONNX Runtime, бенчмарки на датасеті Manga109, статті/reddit/discord-треди про on-device manga OCR). Відповідай українською.

## Точний технічний контекст (фактаж, використовуй його, не додумуй)

**Пристрій:** OnePlus 13, Android, Termux (без root), Adreno 830 GPU. Весь inference — локально на телефоні, без хмари (продукт свідомо privacy-first, дані користувача ніколи не залишають пристрій).

**Наявний рушій:** `llama.cpp`, зібраний Termux-side з OpenCL-бекендом (`GGML_OPENCL=ON`) під Adreno. Vulkan-бекенд **НЕ скомпільовано** в поточній збірці (перевірено напряму — жодних `*vulkan*` бібліотек у build-дереві). Той самий `llama-server` вже успішно й стабільно обслуговує перекладацьку модель `Hy-MT2-7B-Q4_K_M.gguf` (`-ngl 99`, повний GPU-офлоад, ~4.4GB) — тобто OpenCL-бекенд сам по собі робочий і швидкий для **текстових** (не vision) LLM-графів.

**Поточний OCR/переклад-манга пайплайн (baseline, з яким треба порівнювати):**
- Детекція бульбашок: `comic_text_detector` (bbox + mask).
- OCR англійського тексту: `pytesseract` (Tesseract), `lang='eng'`, `--psm 6`.
- OCR японського тексту: `manga_ocr` (Kha-White's manga-ocr, vision-encoder-decoder, ~110M параметрів, чистий CPU inference).
- Геометрична класифікація типу бульбашки (мова/крик/думка): власний CV-алгоритм (Rigaud et al. 2014 контурний аналіз), без моделі.
- Преміум-фічі вже існують і гейтяться тим самим механізмом (`is_entitled("cast_registry")`, донат-гейтинг через Telegram-бот, адмін вручну активує після підтвердженого донату): Cast Registry (реєстр персонажів), Агент-редактор (Gemma 3 4B vision, ~3.5GB, візуальна перевірка верстки), ASR-верифікація наголосів (Whisper Small INT8 через sherpa-onnx — **за історією проєкту цей ONNX-шлях вже був реально розгорнутий і працював на цьому ж пристрої**, хоча на момент написання цього промту прямої перевірки встановленого пакета я не робив — перевір і врахуй це в дослідженні як прецедент "ONNX Runtime на цьому пристрої вже доведено робочий для іншої vision/audio моделі", варте самостійної перевірки, не сліпо вір).

**Уже завантажені, але наразі НЕ використовувані на пристрої моделі** (для орієнтиру по вазі, що телефон реально тягне): `gemma-3-4b-it-Q4_K_M.gguf` + mmproj (~3.5GB, преміум Агент-редактор), `Hy-MT2-7B-Q4_K_M.gguf` (~4.4GB, переклад).

## Реальний, щойно проведений негативний бенчмарк (важливо — не пропонуй те саме знову, поясни ЧОМУ це не спрацювало)

Кандидат **`adambarbato/PaddleOCR-VL-For-Manga-GGUF`** (fine-tune `PaddlePaddle/PaddleOCR-VL`, база `baidu/ERNIE-4.5-0.3B-Paddle`, 0.5B параметрів, лише BF16-квант, реальний завантажений розмір GGUF+mmproj = **~1.8GB сумарно** — model card на HF заявляв 936MB, це виявилось невірним, реальний розмір вдвічі більший, довір власним вимірам, не картці). Заявлена якість (з картки): 70% full-sentence accuracy на Manga109-s crops проти 27% у базової PaddleOCR-VL (порівняння з БАЗОВОЮ моделлю, не з нашим `manga_ocr` — прямого порівняння нема).

Підтримка в llama.cpp з'явилась через PR [ggml-org/llama.cpp#18825](https://github.com/ggml-org/llama.cpp/pull/18825) (змерджено), і вже присутня в поточному Termux-чекауті (`src/models/paddleocr.cpp` існує на дату білда).

**Живий тест на реальному пристрої (сьогодні), три спроби:**
1. Повна сторінка манги (1500×2250 px) через `llama-mtmd-cli`, повний GPU-офлоад (`-ngl 99`, mmproj теж на GPU) → **крах**: `ggml_gallocr_reserve_n_impl: failed to allocate OpenCL buffer of size 12895841280` (~12GB!). Логи прямо попереджають: `WARNING: the CLIP graph uses unsupported operators by the backend` — перелічено UPSCALE, SOFT_MAX, CONT, PERMUTE, ROPE, RESHAPE, MUL_MAT як непідтримувані Adreno OpenCL-бекендом для цього конкретного vision-графа; і `WARNING: flash attention not supported by OpenCL, memory usage will increase`.
2. Та сама повна сторінка, чистий CPU (`-t 4`, без GPU-офлоаду) → обірвано вручну після 20+ хвилин без жодного результату (застрягло на стадії кодування зображення).
3. Маленький crop розміром з одну бульбашку (450×338 px), GPU для текстового декодера + CPU для vision-кодера (`-ngl 99 --no-mmproj-offload`) → **завершився**, але **vision-кодування самого лише маленького crop зайняло 113 секунд** (`mtmd batch encoding done in 113144 ms`), сумарний wall-time ~2 хвилини. При типовій сторінці манги з ~6-7 бульбашками (з історії проєкту: 1293 бульбашки на 194 сторінках ≈ 6.7/сторінку) це екстраполюється в **12-14+ хвилин лише на OCR однієї сторінки**, без урахування перекладу/типографіки.

**Висновок з цього тесту:** проблема не в розмірі моделі (вона крихітна) і не в загальній непридатності Adreno OpenCL (він чудово тягне текстові LLM), а конкретно в **прогалинах підтримки vision-графа PaddleOCR-VL у поточному OpenCL-бекенді llama.cpp** — CLIP-подібна архітектура з нестандартними операціями погано лягає саме на OpenCL. Це може бути специфічним для АРХІТЕКТУРИ (ERNIE-4.5-vision), а не для GGUF/llama.cpp взагалі.

## Що дослідити

1. **Кандидати-моделі**, спеціалізовані чи дотюнені під manga/comic/stylized-font OCR (японська + англійська, бажано обидві), з реальними, перевірюваними бенчмарками якості — ідеально порівняно саме з `manga-ocr` (Kha-White) на Manga109 чи подібному датасеті, не лише "краще за базову версію себе ж". Розглянь як GGUF (llama.cpp), так і ONNX (onnxruntime), і TFLite/NNAPI варіанти — не обмежуйся одним runtime.

2. **Для кожного кандидата — технічна сумісність із цим конкретним пристроєм:**
   - Розмір моделі (реальний, не заявлений — попередь якщо model card підозріло розходиться з типовими розмірами для заявленої кількості параметрів).
   - Архітектура vision-енкодера (CLIP-подібна? SigLIP? власна?) — і чи є відомі issue/скарги на погану підтримку саме в llama.cpp OpenCL-бекенді (шукай на GitHub issues llama.cpp за назвою архітектури + "opencl" + "unsupported operator"/"backend").
   - Якщо ONNX — чи є precompiled `.onnx` ваги (не лише PyTorch/safetensors, які довелось би самому конвертувати), і чи згадується десь успішний запуск через `onnxruntime` з NNAPI/QNN (Qualcomm) execution provider на Android/Adreno конкретно (не просто "підтримує ONNX" загалом).
   - Ліцензія (сумісна з донат-гейтингом преміум-фічі — подивись, як вже вирішено для Gemma 3 4B в цьому ж проєкті: Gemma Terms of Use дозволяють, з атрибуцією).

3. **Чи взагалі варто чекати на кращу OpenCL-підтримку в самому llama.cpp** (перевір відкриті issues/PR по CLIP/vision-graph operator coverage для OpenCL-бекенда, скільки їх активно розробляється, чи є свіжий рух) — vs. переходити на Vulkan-бекенд llama.cpp (компілюється окремо, для Adreno теж підтримується, часто краще покриття операцій ніж OpenCL за останні місяці — перевір актуальний стан) vs. ONNX Runtime як повністю окремий, вже частково доведений на цьому проєкті шлях.

4. **Дай пряму рекомендацію**: чи є ЗАРАЗ реалістичний кандидат, що (а) дає відчутно кращу якість за вже наявний `manga_ocr`/`Tesseract` дует, і (б) реально виконується на Adreno 830 за прийнятний час (орієнтир: не гірше за кілька секунд на бульбашку — преміум-користувач може почекати трохи довше за безкоштовний baseline, але не хвилини). Якщо такого немає — чесно скажи "почекати X" замість вигаданої рекомендації.

## Формат відповіді (жорстко)

1. **Резюме на пів сторінки**: чи є зараз реалістичний кандидат, чи ні, і чому.
2. **Порівняльна таблиця**: модель / розмір (реальний) / runtime / vision-архітектура / відома сумісність з Adreno-OpenCL чи ONNX-NNAPI / заявлена якість vs Manga109 (з джерелом) / ліцензія / рекомендований статус (готовий зараз / чекати на X / не підходить і чому).
3. Розгорнутий розділ по кожному серйозному кандидату (топ-3-5) з посиланнями на джерела (model card, benchmark, GitHub issue/PR).
4. Окремий блок: якщо є сенс переходити на Vulkan-бекенд чи ONNX Runtime замість поточного OpenCL — конкретні кроки/залежності для цього на Termux/Android, і чи це виправдано лише заради цієї фічі чи має ширшу користь для проєкту.
5. Джерела — усі посилання окремим списком в кінці.
